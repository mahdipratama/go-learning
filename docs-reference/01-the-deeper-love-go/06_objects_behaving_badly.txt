A method is just like a function—indeed, it is a function—except that it’s
specialised to a particular data type. You could think of it as a way to use

For example, if you have some Catalog variable representing a book

And that’s exactly what we can do if we turn AddBook into a method. By

method that you can only call on a particular instance: that is, a particular

Methods are purely for convenience and readability: they’re a shorter way
of writing the function call, and one that makes it obvious that we’re doing
something to catalog: in this case, adding a book.
The value that we’re calling methods on is sometimes called an object: that
term doesn’t have any special meaning to Go, but it reminds us that this
isn’t just some static data value, it’s an individual entity with a unique
configuration and an internal state that changes over time, just like objects
in the real world.
I sometimes think of methods as “knobs”, like the controls on a physical
device such as a stove or an amplifier. They’re things you can twiddle to
change the way the object operates. Methods don’t necessarily change the
object, though; they can also just be a way of accessing its information, like
a temperature gauge or a volume indicator.

Pointers
Although there are quite a few small changes here, they’re pretty
superficial: as we’ve seen, methods are really syntactic sugar for functions
where one of the parameters is given a special importance.
Objects as abstractions
In another way, though, the changes we’ve made are fundamental, because
now the Book and Catalog types are not merely a way of storing data.
Adding methods to them gives them behaviour: they can do things. A 
Catalog is not just a passive bunch of books: it also knows how to add and
retrieve books from itself, and how to list all the books it contains.

Go. It’s a way of thinking about programs, or, more specifically,
abstractions.
We saw in a previous chapter that abstractions are useful for making
programs easier to write and reason about, because they hide irrelevant
details behind a simple interface. A function is the simplest kind of
abstraction, but an object is a more sophisticated one.
You could think of objects as “smart data”: data that knows how to
manipulate itself in useful ways. Alternatively, you could regard an object
as “stateful code”: not solely a collection of related functions plus static
data, but a unique entity that can change and develop over its “lifetime”.
Validation
One very useful thing that objects can do to be smart about their data is to
validate it. For example, it might already have struck you that it’s possible
to set the Copies field of a book to a negative number:
Go’s int type represents whole numbers in general, and whole numbers can
be negative, so this is allowed. But it doesn’t really make sense for a
number representing copies of a book to be negative. What would that even
mean? We’re describing a number of physical things, and there can’t be less
than zero copies of a book. So, in this context, book.Copies is invalid: it
can’t be correct.
We could add checks throughout the bookstore code to make sure that every
time we deal with some Book value, it has a non-negative number of copies.
But it would be annoying and wasteful to repeat that checking code in many
places, and we might also want to validate other fields besides Copies.
Also, we’d like to be able to publish the books package as an open-source
software component that other people can import and use in their own Go
book.Copies = -1 // apparently this is fine?programs that deal with book information. It would be a shame if we put a
similar burden of constant checking and re-checking on those users, and if
they forgot to do it in even one place, their programs could produce
incorrect results.
The fundamental problem here is that it’s possible to create a Book value
that is invalid, whatever we’ve decided “invalid” means in this context.
Right now, one way that we’ve identified for books to be invalid is for them
to have a negative number of copies.
Ideally, we’d eliminate this problem by making it impossible for users
(including us, as we’re working on the bookstore code) to set Copies to a
negative number.
But how can we prevent people from setting the Copies field to any int
value that they like? There doesn’t seem to be a way to do that in Go.
And there isn’t, at least not directly, so we’ll have to be a bit more creative.
What if, instead of setting the Copies field by using an assignment
statement, we provided a method that would set Copies for us? In other
words, what if we could write code like this to update the book:
If we had a SetCopies method that took some int parameter, then we could
do the validation—checking that it’s not negative—in one place, once and
for all, and it would be used automatically every time someone updated the
number of copies of a book.

The assignment statement y := x doesn’t create any kind of relationship
between the variables y and x. Instead, it copies whatever value happens to
be in x at the time of the assignment into y. Subsequent changes to x affect
only x.

Adding validation to SetCopies
Sorry about that lengthy detour to introduce and explain pointers, but it was
an important one. Without pointers, we can’t write methods that modify
their receiver. And without pointer methods (that is, methods whose
receivers are pointers, as opposed to values), we can’t write validating
methods, which is what we set out to do.
When validation fails
And we could add some validation logic to SetCopies now, but there’s a
slight problem. What should happen if the provided copies value is invalid?
We have some options. For one thing, we could have SetCopies panic if the
validation fails. That would certainly prevent programs from creating
invalid Book values, but we don’t really want to stop the programs
altogether. It would be better if SetCopies returned some value indicating
whether or not the validation succeeded. That’s because there’s no point
checking that something is valid unless there’s a way to do something about
it if it’s not.
For example, suppose we write a program that lets users enter the details of
new books in stock. If they accidentally type “-1” for the number of copies,
we’d like to be able to detect that invalid entry and invite them to correct it,
instead of crashing and losing all the work they’ve done so far. In general,
well-written programs don’t crash, unless there’s really no alternative.
What should we return as our “valid or not valid” signal? We could use 
bool, as we did with GetBook to indicate whether or not the requested book
book.SetCopies(-1) // what should happen here?was found in the catalog. After all, there are two possible outcomes of
calling SetCopies: either the value was valid or it wasn’t. We could
represent those as true and false, respectively.
That’s not terrible, but if we return just false when the value fails
validation, we can’t include any information about why it was invalid. Yes,
in this context there’s only one way that copies could be invalid: because
it’s negative. But we could imagine other ways (for example, maybe the
user entered “banana” instead of a number).
Ideally, we’d like a solution that works for all kinds of validating methods,
and that means being able to include a message explaining why a given
value isn’t valid.

Here’s what we know so far
It’s been a busy chapter, as you’ve now mastered two key concepts in Go:
methods and pointers. You understand that methods are “syntactic sugar”
for functions that take their first parameter as a receiver, meaning the thing
that the method is about. For example, all the methods on Catalog take a
catalog as their receiver.
You’ve connected this to your existing knowledge about the testing
package, and you can now recognise calls such as t.Fatal as referring to
methods on the *testing.T object: the thing that uniquely identifies each
test and controls its execution.
You also learned what a pointer is, and why we might want to use one in a
Go program. When a function takes some value parameter, it gets a
transient copy of the data, and can’t make lasting changes to it. When it
takes a pointer parameter, though, it’s getting a reference to the original
data, and can use that reference to modify it permanently.
You know that we can use the & (address) operator to create a pointer to a
value, and the * (dereference) operator to find the value that a pointer points
to. And you also know that when this value is a struct, we don’t need to
bother with the *: we can refer to fields directly, and Go will take care of
the dereferencing for us.
