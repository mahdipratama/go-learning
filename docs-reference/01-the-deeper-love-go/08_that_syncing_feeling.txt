8. That syncing feeling
Concurrently reading and changing data can be dangerous, as we saw in the
previous chapter, and the most dangerous thing about it is that it seems
perfectly safe, until it isn’t.
Even if your Go program is not itself concurrent, when you write and
publish a Go package, someone might use it concurrently. We always have
to take data races into account and design our API in such a way that it can
be used safely without users having to take any special precautions.
With this in mind, we now have a few changes to make to the books
package to bring it up to date with the latest version of our catalog API.
First, let’s implement the Sync method, so that we can save any changes we
make to the catalog data.
Writing catalog data to disk
We’ve already written OpenCatalog, which reads JSON data from a disk file
and decodes it to produce a catalog. But as soon as we make any changes to
that catalog (for example, by updating the copies information for a book), it
becomes out of sync with the corresponding file on disk.Sync’s job, then, is to fix that, by putting the two versions of the catalog
back in sync: whatever data is in memory should replace what’s on disk. As
usual, we’ll begin with a test.

the test will always pass, regardless of whether Sync does anything or not.
We hope we won’t write a bug like that, but hope isn’t a strategy. Instead,
we’d prefer to have a more rigorous test that could detect such a problem.
How?
As often happens in software engineering, there’s a complicated answer and
a simple answer. The complicated answer might be to do something like
this:
1. Check that the catalog file doesn’t already exist (if it does, fail)
2. Call Sync to write the catalog file
3. Call OpenCatalog to read the catalog file and check the results
4. Delete the catalog file
This procedure would detect the “Sync does nothing” bug, because it
ensures that data files from previous runs aren’t present before calling Sync.
It’s a little fiddly, though, and makes the test logic more complicated.
The more complicated the test, the more likely it is to contain bugs itself,
and that’s the last thing we want. If you need to write tests for your tests,
then something has gone wrong.
A career-limiting mistakeAlso, deliberately erasing the catalog file is inherently a risky thing to do.
We can imagine introducing a bug in the test that would accidentally cause
it to delete some real catalog file instead of the test artefact.
For example, if the location of the test catalog file were controlled by an
environment variable, someone could accidentally run the tests in a
production environment instead of test, thus deleting all the real data (it
happens).
Needless to say, that unlucky someone could easily be us. Let’s adopt a way
of writing tests that makes such a calamity impossible: a test should never
delete any data that it didn’t create. And more broadly, our tests mustn’t
cause any kind of problem if they’re run in a production environment,
because one day they will be.
So, how can we apply that principle in this test? In other words, how can we
make sure that we only delete data that we created?
Temporary directories with t.TempDir
The ideal thing would be to write the catalog file to a new temporary
directory, unique to this instance of the test, and for that directory to be
automatically cleaned up once the test is complete.

exist before the test starts, because it can’t. And we no longer need to delete
the file afterwards, because when the containing directory gets deleted
automatically, so will the file.

Enabling safe concurrent access to the catalog
As we saw earlier, our new concurrency-safe API design requires a 
SetCopies method on the catalog. We can’t let users grab a Book struct from
the catalog, modify its data, and then write it back into the catalog later,
because that could destroy any changes to the same book made by other
users in the meantime.
Instead, we’ll require all changes to be made by calling methods on the
catalog directly. For example, if a user wants to change the number of
copies of a book available, we’ll give them a SetCopies method to call on
the Catalog, rather than on the Book struct representing the individual book
data.
That way, the book information can’t get out of date while the user is
making changes to it. If SetCopies takes the book ID, it can both retrieve
and update the book within the same method. We’ll still need a way to
ensure that users can’t call SetCopies concurrently on the same book, but

}A locking protocol for shared data
First, let’s recap the problem briefly. We saw in the previous chapter that in
a multi-user environment, a sequence of events like the following can
happen:
1. Amina retrieves book abc’s information by calling GetBook.
2. Bhavana also retrieves book abc from the catalog.
3. Amina modifies abc’s copies information and saves it back to the
catalog.
4. Bhavana modifies abc’s title information and saves it back to the
catalog (destroying Amina’s changes).
The problem occurs because between steps 1 and 3, there are two
potentially different versions of the information about abc. Bhavana gets a
copy of the one in the catalog, but this might differ from the version that
Amina has.
In other words, between steps 1 and 3, it’s not “safe” for anyone else to
access the abc information in the catalog, because their changes could
conflict with Amina’s. The net result of the conflict depends purely on the
relative timing of the two sets of changes: that is, it’s a data race.
The part of a program where such a data race can happen is called, in the
jargon, a critical section. Both Amina and Bhavana’s programs have the
same kind of critical section, between where they get the mutable reference
to the book, and where they relinquish it.
The simplest imaginable lock scheme
Amina’s critical section is between steps 1-3, whereas Bhavana’s is between
steps 2-4. A data race occurs when these two critical sections overlap in
time. We need a way to prevent this.
One very simple, and low-tech, idea would be to have Amina shout out
“Hey, y’all, I’m about to modify book abc. Don’t do anything with abc until
I say it’s okay!” And then later: “All good, I’m done with abc now”.An audio-based protocol like this would work, sort of. It would mean a lot
of shouting, though, and that’s not really ideal: in the best bookstores, a
quiet, studious atmosphere should prevail.
A better scheme might be to have a big whiteboard in the middle of the
store where everyone can see it. When Amina wants to make a change to
book abc, she looks at the board to see if “abc” is already up there. If not,
she writes it on the board. Then she makes her changes, and when she’s
done, she rubs “abc” off the board so other users know it’s once again safe
to modify abc.
What if Bhavana wants to make a change to abc while Amina still has it
“locked” like this? Well, she has to wait. Yes, it might be slightly annoying
for other users to wait until Amina releases the lock, but it’s better than the
catalog data getting corrupted: that would annoy everybody.
And under normal circumstances, no one will need to lock a book for very
long, so most books will spend most of the time unlocked. It’s unlikely that
anyone will have to wait for the lock on a given book, and even if they do,
the waiting time won’t be significant. We don’t expect much contention for
these locks, in the jargon.
It’s a workable scheme, with some caveats. For example, Amina has to be
careful to remember to obtain the lock—that is, to check the board to see if
the book’s ID is up there, and add it herself if not. If she forgets to do this
before modifying the book information, there’ll be a data race.
Also, she has to remember to release the lock afterwards: to rub the ID off
the board. Otherwise, Bhavana will be stuck waiting for the lock forever,
and more and more users will gradually get stuck waiting on the same lock
over time, until eventually nobody can do anything at all (this is called a
deadlock).
Despite these potential problems, locking protocols like this are the simplest
way to prevent data races in real-life concurrent environments. They don’t
usually involve a big whiteboard, but the principle is the same.
Mutexes in GoA lock system like the one we’ve described ensures mutually exclusive
access to some data value, such as book abc. In other words, if I have access
to it, that excludes you having access to it, and vice versa. In the jargon,
then, the lock object that ensures this mutual exclusion is called a mutex.
Go’s standard library includes one of these, as part of the sync package: it’s
called sync.Mutex. Here’s an example of how it’s commonly used:
We needn’t worry at all about how the mutex works internally. We can treat
it as a black box with two methods: Lock and Unlock. We call Lock to get the
lock, we do whatever we need to do with the protected data, and then we
call Unlock to release the lock when we’re finished.
What happens if someone else already has the lock when we call Lock? The
answer is that Lock will wait until the lock becomes available, and then
obtain it for us. Thus, the method call to Lock can take an arbitrary amount
of time to return, and it might not return at all if the lock is never released.
But if it does return, then we now have the lock.
When someone holds the lock on the mutex, it blocks everybody else from
accessing the protected data: that’s a mutex’s job, after all. We should only
acquire the lock right before we need it, and release it as soon as possible
afterwards. We should also avoid doing anything too time-consuming
during this period, to avoid unnecessarily blocking the lock for other users.
Both reads and writes need to be lock-aware
It sounds like a mutex will help us to ensure safe concurrent access to the
catalog, but before we do that, there’s one more point we need to talk about.
When do we need to acquire the mutex lock? Is it only when we want to
change the data, or is it also when we’re reading it?
var mutex sync.Mutex 
mutex.Lock() 
// do something with data 
mutex.Unlock()You might be tempted to say that it’s only when we’re changing the data.
After all, if we’re just reading, we’re just reading! Why would we need to
get a lock on something that we’re not changing?
But that idea doesn’t work, because even though we’re just reading,
someone else might concurrently be writing. While someone has the “write
lock” on the data, it’s not safe for anyone else to read it. By “not safe” I
mean that the data we’re looking at it might be in the middle of being
changed, and we could see partial or invalid results because of this.
In other words, a data race exists when two or more users (or different parts
of the same program) are accessing the same piece of data concurrently, and
at least one of those accesses is a write. To prevent a race, the data must be
protected by a mutex, and all accesses must obtain the lock, even reads.
Read locks and write locks
You could imagine, then, that every piece of code accessing the data,
including reads, would have to call Lock to acquire the mutex, waiting if
necessary. But, since data is usually read more often than it’s written, most
accesses are reads. That seems rather wasteful: it’s perfectly fine for lots of
people to read the same data concurrently, as long as no one’s writing it.
Why do we need an exclusive lock if we’re only reading?
We don’t. We only need to prevent other people writing the data while we
read it; we don’t care how many other people read it at the same time.
Ideally, we’d be able to get two different kinds of lock on a mutex:
an “exclusive” lock for writing, that can only be held by one person at
a time
a “shared” lock for reading, that can be held by many people
simultaneously, as long as no one also has an exclusive lock
For example, our find and list programs would only need to lock the
catalog for reading, so they can hold this lock at the same time as other
readers: it needn’t stop anyone else reading the catalog, only writing to it.
It’s perfectly safe to have lots of different users all reading the catalog atonce. But a program that writes to the catalog, such as copies, would need
to lock it for writing, thus preventing concurrent writes and reads.
Slightly confusingly, a “lock for reading” is often referred to for short as a
read lock. But a read lock doesn’t prevent reads, as one might easily
assume: instead, it prevents writes! Sorry about that. Similarly, a “lock for
writing” is often called a write lock, but it doesn’t prevent writes: it prevents
reads.
If you, like me, sometimes get these terms mixed up, think of it this way:
when you want to read, you need a read lock, and when you want to write,
you need a write lock.
Go’s sync.RWMutex type
In Go, the type that provides this two-tier locking is called sync.RWMutex.
Write locking (exclusive locking) works exactly the same way as a regular
mutex: we call Lock to lock it for writing, and Unlock to release it. But 
RWMutex has an additional pair of methods for read locking: RLock / RUnlock.
Using an RWMutex can perform much better than a Mutex in situations where
reads are more common than writes. That’s because a read lock on an 
RWMutex still allows concurrent reads, whereas a regular Mutex (or a write
lock on an RWMutex) doesn’t.
It sounds like RWMutex is the right choice for our catalog, since we envisage
book information being read a lot more often than it’s changed.
We could modify the Catalog type to hold an RWMutex as well as the map
data, and we could add the required calls to Lock / Unlock or RLock / RUnlock
to its methods. We can imagine getting this wrong, of course, just like
anything else. How can we actually test that the catalog is safe for
concurrent access?
Well, one way would be to access it concurrently and see if anything blows

we’ve correctly updated the code to be lock-aware, there should be no data
