In the previous chapter we developed the idea of the catalog as a smart
repository for book data. It’s now become an object that provides methods
for users to list, query, and add books. We also extended the Book object to
allow (and validate) changes to the details of a particular book: for example,
updating the number of copies.
That’s nice. But now that we can make changes to the catalog data, we have
a new problem to solve: how to make those changes persist.
Making persistent changes
Right now, the catalog is initialised by calling GetCatalog, and its contents
are determined by the code of that function. That won’t work for a real
bookstore, where we expect the book information in the catalog to change
dozens of times a day. It wouldn’t be practical to keep asking the developers
to change the source code and release a new version of the books package
every time someone buys a book!
Besides, we want the books package to be usable by many different stores,
each with their own ever-changing catalogs. We’re going to need some wayto store this information outside of the Go program itself.
Storing the catalog on disk
Suppose we wrote a program to add a new book. We could ask the user to
enter the title, author, and other details of the new book, and then we could
add the new book to the catalog using the AddBook method we wrote in the
previous chapter.
What happens, though, when the user next runs the find program to search
for the new book? Well, nothing, because find gets its catalog data from the
GetCatalog function, and that won’t have changed. The new book
information has been lost.
That’s because we’re storing the catalog data in a map, and like all variables
in a Go program, its contents are only preserved as long as the program is
running. Once the program exits, everything it stored in memory is wiped,
to make room for other programs to store their own variables.
That makes sense, but for our bookstore we’ll need a way to store our
catalog data in a file on disk, not in the program’s temporary memory. Once
we have that, we’ll be able to make persistent changes to it.
To do this, we’ll need a few new bits of Go knowledge: how to read and
write disk files, how to turn a Go variable into something that can be stored
in a file, and how to read that stored data back into a variable.

The defer keyword
Assuming there wasn’t an error, and that file has now been initialised to a
handle representing the data file, we then do this:
file, err := os.Open(path)
if err != nil { 
    return nil, err 
}
defer file.Close()It’s good practice to call the Close method on a file handle when we’re done
with it, so that Go knows we won’t be accessing that file anymore and it can
reclaim the associated memory.
So, in theory, we could have called file.Close() directly when the function
exits. But there isn’t just one exit point for this function: there are three. It
can return because there’s an error from os.Open, or it can return because
there’s an error from Decode, or it can return because it’s done and
everything’s okay. We need to close the file in all three of those situations.
It would be annoying to have to write file.Close() in three different
places, so that’s what the defer keyword takes care of. It means “be sure to
call file.Close() on exit, however and wherever this function happens to
return”.
defer is quite common in Go programs, because there’s often some kind of
cleanup we need to do when we’re done with a resource, such as a file.
Using defer to schedule the cleanup for later means that we don’t have to
worry about all the different ways the function can exit: the deferred
statement will be executed regardless.

Why are we passing a pointer to the catalog, rather than the catalog itself?

Winning the change race
Specifically, imagine the following sequence of events:
1. Amina retrieves book abc’s information by calling GetBook.
2. Bhavana also retrieves book abc from the catalog.
3. Amina modifies the book’s copies information and saves it back to the
catalog with the ID abc.
4. Bhavana modifies the book’s title information and saves it back to the
catalog with the ID abc.
Now, what happens to Amina’s change? It gets lost, because Bhavana
overwrites all the information for abc with the Book struct she retrieved at
step 2, including the copies information.
catalog := books.OpenCatalog(...) 
book := catalog.GetBook(ID) 
book.SetCopies(copies) 
catalog.Update(book) 
catalog.Sync(...)It’s a data race, like we saw in the chapter on maps where parallel tests
started flaking because they were concurrently modifying the catalog. In
this case, whoever saves their changes last “wins” the race, in the sense that
all other users’ changes are lost.
The fundamental problem here is that we can hand out copies of the same 
Book struct to more than one user at a time, and they can make independent
changes, which then race to make it back into the catalog. As long as this is
possible, we can’t guarantee that data from concurrent changes won’t be
lost.
This seems unsatisfactory, so what can we do to prevent it? Well, we can’t
allow more than one mutable reference to a book to exist at once. That is,
we can’t let users get a modifiable copy of a book’s information, hang on to
it for as long as they like and make all sorts of changes, and then use that
data to overwrite whatever’s currently stored in the catalog for that book.
In some programming languages, such as Rust, this safety property is
enforced by the language itself. That is, if you try to write a Rust program
that creates more than one mutable reference to the same data at a time, it
won’t compile. That fundamentally isn’t a safe thing to do, so Rust won’t
let us do it.
Go doesn’t have this useful feature, sadly, so if we want to avoid data races
in our programs, we’ll have to prevent them ourselves.
Making catalog changes atomic
To be clear, the problem is not that users can concurrently modify book
information in the catalog, in principle. The problem is that there’s a section
of code in such a program where it’s not safe for anyone else to make a
change to the same book, and we have no way of preventing them from
doing so.
At least, not if we provide a method like UpdateBook. Let’s take that away,
and require that any change to a book’s information be made atomically—
that is, in a single step, so that we don’t have to hand out mutable
references.So, for example, we could provide a SetCopies method on the catalog,
instead of an individual book. The potential for a data race could still exist
inside that method, if it’s called concurrently, but we can solve that problem
later. If we allow users to Update the catalog willy-nilly, though, we can
never guarantee to avoid races.
That brings us back to the original version of the copies program we saw,
and here it is again in brief:
This particular set of methods and behaviours for Catalog gives users the
ability to do what they need to do, but in a concurrency-safe way.
In the jargon, this is called the catalog’s API (Application Programming
Interface), meaning the set of functions and methods that an application
program such as copies would use to manipulate the information in the
catalog. Designing good APIs is a big part of building good software, and
probably one of the hardest.
The best way I know to figure out what the API of some abstraction such as
the catalog should be is to do what we’ve done here: write the code that
calls the API first. We know what we want to do, so we imagine the
appropriate methods and functions that would achieve it.
