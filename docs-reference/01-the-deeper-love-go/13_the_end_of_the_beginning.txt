As with all abstractions, the job of the client is to hide irrelevant details
from the code that uses it. When we’re writing a find program, we don’t
want to be concerned with how to construct the request URL, how to
interpret the response status, how to decode the body, and so on. We’d
prefer to work with something that acts just like a catalog: we can call 
GetBook on it and get the book we want, or an error explaining why not.
Having a client like this would make it easy to write programs like find, 
list, and so on, as well as dramatically simplifying our tests. It seems

The any interface
You know that Go’s standard library often uses abstractions such as 
io.Reader, representing any type of value that we can read bytes from.

func json.Unmarshal(data []byte, v any) errorThese special polymorphic (“many-shaped”) types are called “interfaces”,
because they’re defined in terms of what we can do with the thing. For
example, the io.Reader interface stands for any type that we can read from,
and we can do that if the type has a Read method.
That’s how we create an interface type: by listing a bunch of methods that a
type must have in order to implement (that is, satisfy) the interface. Let’s
look at io.Reader’s definition, then, just for fun:
Very simple! There’s only one method required, named Read, and any type
that has it is an io.Reader. As we’ve seen, lots of things have a Read
method: files, HTTP response bodies, and so on. They can all be used
where a function expects an io.Reader.
What about the any interface, then? What methods does a type need to have
in order to be an any? See if you can work it out from the definition:
It’s an empty list. Any type at all implements this interface. Note that the
interface is not saying the type must have precisely no methods: instead, it
just says that no particular methods are required to be an any. Thus, every
type satisfies this requirement.
Because of this, any is the least restrictive possible interface, and thus (in
some ways) the most useful.
As I mentioned, you can learn much more about interfaces in Know Go if
you’re interested, but all we need to know for this program is how to
declare a parameter to MakeAPIRequest that can be any type. Now we can do
exactly that:
type Reader interface { 
    Read(p []byte) (n int, err error)

TOCTOU for two
You might be tempted to add API endpoints that straightforwardly replicate
what we had on the catalog: something like getcopies/ID and 
/setcopies/ID/N to set N copies.
But is this really good enough? For example, suppose that Amina is adding
new stock to the system, and she has two copies of Caroline Graham’s The
Killings at Badger’s Drift to process. What is the correct new stock level of
this book? It depends on how many copies are already in stock.
Amina first has to find that out, using some hypothetical getcopies
program:
getcopies kbd
8 copies in stock
So, counting the two new copies, that’s 10 in total. Now Amina uses a
hypothetical setcopies program to update this:
setcopies kbd 10
Can you see the problem? What Amina doesn’t know is that, concurrently
with this, Bhavana is selling a copy of the same book at the next till over.
Bhavana checks the current stock level:
getcopies kbd
8 copies in stock
She hands over the book to the delighted customer, and runs setcopies to
reflect the fact that the stock level just dropped by one:
setcopies kbd 7Now, when Amina and Bhavana have both finished their respective
transactions, what is the true stock level? It started at 8, we added two and
subtracted one, so I hope we agree it’s now 9. But the system doesn’t agree.
The system’s view of the stock level depends on whose transaction
completed last.
If Amina’s finished last, then the catalog will show the level she set: 10. On
the other hand, if Bhavana’s overwrote Amina’s, then the catalog will show
7. Both answers are wrong, and the saddest thing is that we don’t even
know which wrong answer we’ll get until it happens.
I’m sure that by now you recognise the problem as a data race. This specific
kind of race is called a TOCTOU (Time-Of-Check-to-Time-Of-Use) error.
The information Amina and Bhavana have about the stock level is only as
good as the last time they checked it, and by the time they use that
information to update the catalog, it could well be out of date.
It’s as though you check your bank account one day, and you find that the
balance is exactly a dollar. Then, a few weeks later, you withdraw exactly a
dollar. Does this result in you going overdrawn? Who knows? It’s entirely
possible (sad to say). It depends what else happened between the “time of
check” and the “time of use”.
Stale and poisoned locks
How do we fix this? We’ve solved previous data races by using a mutex
lock on the catalog. Would that work here?
Well, for Amina’s change to be atomic (“not split”) she would have to first
obtain the lock with the getcopies query, and then hold it until it’s released
by the call to setcopies. The state of that lock prevents Bhavana, or anyone
else, reading or modifying the catalog for any book, until Amina completes
her whole transaction.
That solves the TOCTOU problem, but it potentially creates a worse one:
the lock becoming stale. Amina might get distracted, or finish her shift, or
her computer might crash; any number of things could prevent her fromrunning setcopies to release the lock. Once the lock goes stale, anyone who
tries to obtain it becomes blocked.
This can quickly lead to a deadlock, in which everyone is waiting for locks,
and because no one can proceed, anyone holding a lock can’t release it. The
whole system is logjammed. In Go, the runtime detects this situation and
terminates the program, because it’s logically impossible for it to continue.
Critical sections must be as fast as possible, and ideally never panic or be
interrupted. If a goroutine panics while holding a lock, the mutex is said to
be poisoned: any other goroutine that tries to obtain it will simply sleep
forever, like Snow White.
While locks can be very useful, then, they must only be held for short
periods, and “short” here means in computer time, not human time. Even if
Amina holds the lock for only a minute or two, that’s probably already long
enough to disrupt bookstore operations.
Atomic changes
A better solution here is to re-think what Amina and Bhavana are really
doing. Yes, they’re both reading and then writing copies information for a
book, but it’s in service of two different goals. Amina wants to add two
copies to the store’s current stock, whatever it happens to be at the time.
Bhavana wants to subtract one copy from the store’s current stock,
whatever it happens to be at the time.
When you phrase the problem that way, it opens up a new idea: what if our
programs (and corresponding endpoints) were not getcopies and 
setcopies, but instead, let’s say, addcopies and subcopies?
Now, when Amina runs addcopies kbd 2, the API server need only hold the
lock for as long as it takes to add 2 to the current stock level, whatever it is.
And when Bhavana runs subcopies kbd 1, she only blocks bookstore
operations for as long as it takes to subtract 1—provided, of course, that
there is at least one copy in stock.This sounds like a more workable plan. We’ll still need a getcopies
program, for checking stock levels, but we’ll replace setcopies with two
programs, addcopies and subcopies. We’ll say that adding copies always
succeeds, but that subtracting copies can fail (leaving the catalog
unchanged) if the result would be less than zero stock of a book.

Sentinel errors
A smarter handler would distinguish between these two different error
situations, and return an appropriate status code for the “not enough copies”
case: perhaps StatusBadRequest. But how can we make that distinction? It’s
not enough to know that err is not nil: which error is it?
Up to now, we’ve never really cared what an error specifically was, only
that it wasn’t nil, because errors are information for users. But now the
program itself needs to be able to tell one kind of error from another and
take different actions.

Know Go
Things are changing! Go beyond the basics, and master the new generics
features introduced in Go. Learn all about type parameters and constraints
in Go and how to use them, with this easy-to-read but comprehensive guide.
If you’re new to Go and generics, and wondering what all the fuss is about,
this book is for you! If you have some experience with Go already, but want
to learn about the new generics features, this book is also for you. And if
you’ve been waiting impatiently for Go to get generics already so you can
use it, don’t worry: this book is for you too!
You don’t need an advanced degree in computer science or tons of
programming experience. Know Go explains what you need to know in
plain, ordinary language, with simple examples that will show you what’s
new, how the language changes will affect you, and exactly how to use
generics in your own programs and packages.
As you’d expect from the author of The Deeper Love of Go and The Power
of Go: Tools, it’s fun and easy reading, but it’s also packed with powerful
ideas, concepts, and techniques that you can use in real-world applications.
