10. It’s a lock
 
(original photo by BazzaDaRambler, licensed under Creative Commons)
In the previous chapter we learned the fundamentals of concurrent
programming in Go, using goroutines and the go statement. Sharing data
between goroutines is useful, but creates potential dangers, just like sharing
a railway track between trains.
And we saw that one way to eliminate these risks is to use a mutex, which
acts like the token that grants trains exclusive access to a section of track. If
each goroutine acquires the mutex before accessing the shared data, no data
races—no collisions—can arise.
This sounds like just what we want for our bookstore project, where
multiple sales terminals need to be able to safely read and update the book
catalog. Let’s see if we can add a mutex to our books package to make this
possible.
Smoke testingAs usual when making any change to our code, we’ll start with a test. To
prove that adding a mutex prevents data races, we’ll first need to show that
a data race exists without it.
If we write a test that triggers the race detector by making concurrent
accesses to the catalog, then when we add the mutex, the race should go
away. That’ll give us confidence that we’ve solved the problem correctly.

executing task controlled by the scheduler, as we saw in the previous

We store a pointer to the mutex rather than the mutex value itself, and it’s
worth taking a moment to think about why that’s necessary.
Every method that accesses the catalog now needs to be mutex-aware: in
other words, it’ll need to get the lock before trying to read the map data.
Take GetBook, for example:
GetBook takes a Catalog value, not a pointer. So, as we saw in the earlier
chapter discussing pointers, when this method is called, it will receive a
copy of the catalog.
And it never makes sense to copy a mutex. If we did, then each goroutine
would be getting the lock on its own copy of the mutex, and that would
bypass the original mutex altogether.
It would be as though the train driver 3D-printed her own token and set out
blithely across the narrow bridge, believing she had exclusive access to it.
That’s no way to run a railroad, and it won’t work for the bookstore either.
That’s why we need to make mu a pointer field here. You can copy a pointer
all you want, but all the copies will still point to the same mutex, so we’re
safe.

What’s going on?
Exported and unexported fields
The message about “unexported” fields is Go’s way of saying that the mu
and data fields are private: that is, they’re internal to the books package.
They’re not “visible” to code outside the package (such as this test helper)
so we can’t refer to them directly.
This visibility is controlled by the names of the fields: if they began with a
capital letter (Mu) they’d be exported, but since they begin with a lowercase
letter (mu) they aren’t.
Which is the right choice for these particular fields? Should we change
them to be exported, or keep them private? One way to answer this question
is to ask “Would users of the books package want to read or write these
fields? If so, would it be sensible to let them?”
The Path field is capitalised, so it’s already exported, and that makes sense:
we can imagine users wanting to change the location of the disk file
associated with the catalog.
What about the data field? Users might want to access data directly, for
example, but people often want things that aren’t good for them. And we

Mismatched lock/unlock calls
It’s easy to make a mistake with an RWMutex and accidentally call Unlock
when you mean RUnlock, or vice versa. If that happens, though, the runtime
will panic the program:
fatal error: sync: RUnlock of unlocked RWMutex
Similarly, if you try to unlock a mutex that you haven’t previously locked,
that’s also a fatal error:
fatal error: sync: Unlock of unlocked RWMutex
This makes sense, since in both cases the errant unlock must be a mistake.
Once a program gets its locks in a twist, things are likely to go painfully
wrong pretty quickly. The only safe thing to do is panic.

The real benefit of this approach is not the mutex locking, as such, because
users could have done that themselves. It’s the fact that the mutex is
invisible: the locking is all internal, so users don’t need to worry about it, or
even know that it’s happening.
As we saw in a previous chapter, the Go language doesn’t have some of the
built-in safeguards provided by other languages (notably Rust). That’s by
design, because Go mostly favours simplicity over safety, and where safety
isn’t critical that trade-off makes sense.But where safety is critical, such as in a multi-user bookstore system, we
have to be extra vigilant. When we publish reusable Go libraries like the 
books package, we can’t know what kind of programs they’ll end up being
part of. Even when a package doesn’t contain concurrent code itself, we
should always try to ensure that it’s safe to use concurrently.
To do this, we need to make its API safe by default. The most reliable way
to do this in Go is usually to define a struct with private fields guarded by a
mutex, and accessible only by mutex-aware methods.

You now know how to use Go’s built-in race detector, via the -race flag, to
automatically detect data races, and how to prevent them by writing locking

write locks, and how to implement both using the sync.RWMutex type.
As a result, you have a thorough grounding in the knowledge you need to
make your packages concurrency-safe, and also to write safe and correct
concurrent Go programs.
