We’re making rapid progress: we have both the client and the server code
for the “list all books” feature. But we know we’d like to be able to do other
things, too. For example, we’ll need to be able to get information on a
specific book, using our find program.
We have all the code we need to get a specific book by ID: that’s part of the 
Catalog, and the server now has access to the catalog, so that’s no problem.
But we have a couple of hurdles to get over before we can get find
working.
One is that right now the server always responds to any request with the list
of all books. That’s fine for list, since that’s what it wants, but find needs
a different response. It needs the server to send back information about
exactly one  book, specified by its ID.
We could write another server program, of course: one that treats every
request as a “find” request. But it would be annoying to repeat all of the
code involved in starting and running the server, and even worse, the two
servers would be competing for access to the same catalog file. As soon as
we wrote a server that could modify  the catalog, we’d have a data race, so
that solution is no good.
Much better would be a single server with exclusive access to the catalog,
but one that could distinguish between two (or more) kinds of request: for
now, “find” requests and “list” requests. Then it could respond to each with
the appropriate data: the list of all books, for “list” requests, or the data on a
specific book, for “find” requests.
How could the client  convey to the server which kind of request it’s
making? One idea is to include that information in the URL. Recall from
the previous chapter that a URL identifies not only some server (specified
by host address and port number), but also some specific r esour ce ,
identified by name (called the URI).

Multiplexing with ServeMux
Distinguishing between different kinds of requests, and routing each to a
request-specific handler, is called multiplexing , and Go’s http package
func handle(w http.ResponseWriter, r *http.Request) { 
    if r.URL.Path == "/list" { 
        fmt.Fprintln(w, "You asked for /list") 
    } else if r.URL.Path == "/find" { 
        fmt.Fprintln(w, "You asked for /find") 
    } else { 
        fmt.Fprintln(w, "You asked for something else!") 
    } 
}includes a service multiplexer named ServeMux that we can use for exactly
this purpose.
Here’s how we could use a ServeMux to multiplex two kinds of request—
two different r outes —in our “hello, world” server:
First, we use NewServeMux to create a new multiplexer that we call mux.
Next, we call mux’s HandleFunc method to install a new route, /hello, and
we map it to the hello handler. Similarly, we use HandleFunc again to map 
/goodbye to the goodbye handler.
We can keep doing this as many times as we want, mapping different URL
patterns to their request-specific handler functions. Once we’ve finished
setting up all the routes we want, we call ListenAndServe to start our server,
and we pass it mux as the handler argument.
When we run this program, mux will intercept each request and look at the
URI part to see if it matches /hello. If so, it will invoke the hello handler,
which sends the message “Hello, world”.
func main() { 
    mux := http.NewServeMux() 
    mux.HandleFunc("/hello", hello) 
    mux.HandleFunc("/goodbye", goodbye) 
    http.ListenAndServe("localhost:3000", mux) 
} 
 
func hello(w http.ResponseWriter, r *http.Request) { 
    fmt.Fprintln(w, "Hello, world") 
} 
 
func goodbye(w http.ResponseWriter, r *http.Request) { 
    fmt.Fprintln(w, "Goodbye, world") 
}On the other hand, if it matches /goodbye, that triggers the goodbye handler
to print “Goodbye, world” instead. And if neither of those routes is
matched, the mux will automatically respond with 404 page not found.

HTTP handler panics are recovered
By the way, since panic usually terminates the program, you might wonder
why the server doesn’t stop running when this happens. If we look at the
terminal where the server is running, we see this:
2025/06/25 13:20:38 http: panic serving [::1]:56195: ID "bogus" not 
found 
...
It does at least report this error, which is helpful. But why didn’t the
program exit?
Well, panics can happen for all sorts of reasons, and we wouldn’t
necessarily want one  panicking request to shut down the server for all other
users. Indeed, that would be a potential denial-of-service vulnerability. If
someone figured out how to craft a request that panicked the server (as we
just have), they could shut it down any time they wanted to.
To prevent this, Go’s HTTP server r ecovers  panics in handlers. We needn’t
worry about exactly how this works, since we don’t usually need to do it inour programs. The upshot is that panics are reported, but the server keeps
on running.
